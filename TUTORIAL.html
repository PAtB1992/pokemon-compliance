Tutorial: Pokémon Compliance Center von Grund auf verstehen

Dieses Tutorial geht jede Datei im Projekt durch, in der Reihenfolge, in der man sie beim echten Bauen anlegen würde — und erklärt bei jedem Schritt warum er nötig ist, nicht nur was der Code tut. Du brauchst kein Vorwissen zu NestJS, TypeORM, Angular Signals, Cypress oder CI/CD-Pipelines — jedes Konzept wird eingeführt, sobald es zum ersten Mal gebraucht wird.

Wie dieses Tutorial funktioniert

Öffne parallel dazu das Projekt in WebStorm (oder deinem Editor). Jeder Schritt nennt oben den genauen Dateipfad — öffne die Datei dort und lies mit. Der Code in diesem Tutorial ist identisch mit dem, was schon in deinem Projekt liegt; du musst nichts abtippen, es sei denn du willst es zur Übung nachbauen.

Das Prinzip hinter jedem Schritt: Ich beantworte immer drei Fragen, bevor Code gezeigt wird: Welches Problem löst dieser Baustein? Was würde ohne ihn schiefgehen? Und warum genau an dieser Stelle im Ablauf, nicht früher oder später? Das ist derselbe Dreiklang, den du im Interview für den "Architectural Design Proposal"-Schritt brauchst.
Reihenfolge ist bewusst gewählt: Wir bauen von innen nach außen — zuerst das Datenmodell, dann die reine Business-Logik (ohne Datenbank!), dann die API-Schicht drumherum, dann das Frontend, zuletzt Tests/CI. Das ist keine willkürliche Reihenfolge: Es ist die Reihenfolge, die geringste Abhängigkeiten zuerst baut, sodass jeder Schritt isoliert verständlich und testbar ist, bevor der nächste draufkommt.

Die große Vogelperspektive

Bevor wir in Dateien eintauchen: Dieses Projekt besteht aus zwei komplett getrennten Programmen, die nur über HTTP miteinander reden — genau wie in der echten Stellenausschreibung.

TeilRolleLäuft auf
backend/NestJS-API: hält die Daten, prüft die Business-Regeln, ist die "Wahrheit" des Systemshttp://localhost:3000
frontend/Angular-App: zeigt Daten an, schickt Nutzereingaben als HTTP-Requests ans Backendhttp://localhost:4200

Warum getrennt und nicht eine einzige Anwendung? Weil so beide unabhängig skalieren, deployen und getestet werden können — das Frontend könnte theoretisch auch eine mobile App sein, ohne dass sich am Backend etwas ändert. Das ist auch der Grund, warum main.ts im Backend cors: true setzt (dazu gleich mehr) — zwei getrennte "Origins" im Browser-Sinn müssen sich explizit die Erlaubnis geben, miteinander zu reden.

Schritt 1Warum NestJS & Dependency Injection

Bevor wir Code sehen, die wichtigste Denkweise, ohne die der ganze Rest des Backends wie willkürliche Magie wirkt: Dependency Injection (DI).

Das Problem, das DI löst

Stell dir vor, du schreibst einen ComplianceService, der Daten aus der Datenbank braucht. Ohne DI würdest du im Service selbst schreiben: const repo = new Repository(...). Problem: Jetzt ist der Service fest ("hart") mit einer konkreten Datenbank-Verbindung verdrahtet. Willst du ihn in einem Test ohne echte Datenbank ausführen (wie wir es in Schritt 16 tun), hast du keine Möglichkeit, diese Verbindung durch eine Fake-Version zu ersetzen — sie steckt fest im Code.

Die Lösung

Bei DI bittet eine Klasse nur darum, etwas zu bekommen ("ich brauche irgendein Ding, das sich wie ein Trainer-Repository verhält"), baut es aber nicht selbst. Ein zentraler "Container" (bei NestJS: der IoC-Container, IoC = Inversion of Control) entscheidet zur Laufzeit, welche konkrete Instanz geliefert wird. Für den echten Betrieb ist das die echte Datenbank-Anbindung; für einen Test kann es ein simples Mock-Objekt sein — der Service selbst merkt den Unterschied nicht. 

// OHNE DI (schlecht - fest verdrahtet):
class ComplianceService {
  private repo = new TrainerRepository(realDatabaseConnection); // fest einprogrammiert
}

// MIT DI (NestJS-Stil - der Container entscheidet):
@Injectable()
class ComplianceService {
  constructor(@InjectRepository(Trainer) private repo: Repository<Trainer>) {}
  // "Ich brauche ein Repository für Trainer" - WIE das beschafft wird, ist nicht meine Sache
}
Warum das der allererste Schritt ist: Jede einzelne Datei im Backend, die du gleich siehst (@Injectable(), @Controller(), Konstruktor-Parameter mit Typen) ist Syntax rund um genau dieses eine Prinzip. Wenn du DI einmal verstanden hast, ist der Rest von NestJS "nur" Vokabular.

Warum NestJS und nicht plain Express?

Express (die Grundlage, auf der NestJS standardmäßig läuft) gibt dir keine Struktur vor — jedes Team baut Ordner/Schichten anders. NestJS erzwingt eine Struktur (Module, Controller, Provider) und bringt DI, Decorators und Testing-Utilities eingebaut mit. Für ein Enterprise-Projekt mit vielen Entwicklern und langer Laufzeit (wie die Cloud-Plattform aus deiner Ausschreibung) ist erzwungene Konsistenz mehr wert als die Freiheit, die Express bietet.

Schritt 3main.ts — der Einstiegspunkt

backend/src/main.ts
import { NestFactory } from '@nestjs/core';
import { ValidationPipe } from '@nestjs/common';
import { AppModule } from './app.module';

async function bootstrap() {
  const app = await NestFactory.create(AppModule, { cors: true });
  app.useGlobalPipes(new ValidationPipe({ whitelist: true, transform: true }));
  await app.listen(3000);
}
bootstrap();

Das ist die allererste Zeile Code, die ausgeführt wird, wenn du npm run start:dev tippst. Vier Dinge passieren hier, jedes aus einem konkreten Grund:

ZeileWasWarum
NestFactory.create(AppModule)Baut den kompletten DI-Container aus AppModule aufAlles, was die App braucht, hängt letztlich an diesem einen Wurzel-Modul (siehe Schritt 4)
{ cors: true }Erlaubt Requests von anderen Origins (z. B. localhost:4200)Ohne das würde der Browser Requests vom Angular-Frontend blockieren — Sicherheitsmechanismus der Browser, nicht von NestJS
ValidationPipePrüft automatisch jeden eingehenden Request-Body gegen die Regeln, die wir gleich in DTOs definieren (siehe CheckRosterDto in Schritt 10)Verhindert, dass fehlerhafte/böswillige Daten überhaupt bis in deine Business-Logik vordringen — "Shift-Left" für Datenqualität
app.listen(3000)Startet den HTTP-Server auf Port 3000Ab hier kann das Frontend (oder curl) Requests schicken
Häufiger Anfängerfehler: whitelist: true in der ValidationPipe bedeutet: Felder, die NICHT im DTO definiert sind, werden aus dem Request-Body automatisch entfernt statt einen Fehler zu werfen. Das ist Absicht (verhindert versehentliches "Massenzuweisen" unerwarteter Felder), verwirrt aber, wenn du dich fragst, warum ein zusätzliches Feld einfach "verschwindet" statt einen Fehler zu zeigen.

Schritt 4AppModule & Datenbankanbindung

backend/src/app.module.ts
@Module({
  imports: [
    TypeOrmModule.forRoot({
      type: 'better-sqlite3',
      database: ':memory:',
      entities: [Trainer, PokemonEntry, TournamentRule, Violation],
      synchronize: true,
    }),
    TrainersModule,
    RulesModule,
    ViolationsModule,
    ComplianceModule,
    EventsModule,
    SeedModule,
  ],
})
export class AppModule {}

Das Wurzelmodul der Anwendung. Ein NestJS-@Module ist im Kern nur eine Liste: "Diese anderen Module gehören zu mir (imports), diese Klassen kann man von außen bei mir anfragen (providers/controllers), und das hier gebe ich nach außen weiter (exports)." AppModule importiert alle Feature-Module (Trainers, Rules, ...) — das ist die Stelle, an der aus vielen kleinen, unabhängigen Bausteinen eine einzige Anwendung wird.

Warum TypeOrmModule.forRoot() genau hier? Die Datenbankverbindung ist eine globale Ressource, die viele Module brauchen (Trainers, Rules, Violations, Compliance greifen alle auf Entities zu). Sie gehört deshalb ins Wurzelmodul, nicht in ein einzelnes Feature-Modul — sonst müsste jedes Feature-Modul seine eigene Verbindung aufbauen.
synchronize: true — nur zum Lernen! Diese Option lässt TypeORM das Datenbankschema automatisch aus den Entities ableiten und bei jedem Start neu erzeugen. Praktisch zum Lernen (kein manuelles Schema-Management nötig), aber in echten Projekten mit persistenter Datenbank gefährlich: Es könnte unkontrolliert Spalten löschen/ändern. In Produktion nutzt man stattdessen versionierte Migrations (siehe Kapitel "TypeORM" im Interview-Guide) — bewusster, nachvollziehbarer, reviewbar.

Schritt 5Was ist eine Entity/ein ORM?

Bevor wir die erste Entity-Datei öffnen: Warum benutzen wir überhaupt TypeORM, statt direkt SQL-Befehle zu schreiben?

Das Problem

Ohne ORM würdest du an vielen Stellen im Code Strings wie "SELECT * FROM trainer WHERE id = ?" schreiben. Das hat drei Probleme: Tippfehler in Tabellen-/Spaltennamen fallen erst zur Laufzeit auf (nicht beim Kompilieren), du musst SQL-Ergebnisse manuell in TypeScript-Objekte umwandeln, und Änderungen am Datenmodell (neue Spalte) erfordern, jede betroffene SQL-Stelle im ganzen Projekt manuell zu finden.

Die Lösung: ORM (Object-Relational Mapping)

Ein ORM wie TypeORM lässt dich das Datenmodell einmal als TypeScript-Klasse beschreiben (eine "Entity") und generiert SQL automatisch daraus. Du schreibst repo.findOne({ where: { id } }) statt rohes SQL — typsicher, mit Autovervollständigung in der IDE, und die Entity-Klasse ist die einzige Quelle der Wahrheit für das Datenmodell.

Schritt 6Trainer & PokemonEntry

backend/src/trainers/trainer.entity.ts
@Entity()
export class Trainer {
  @PrimaryGeneratedColumn('uuid')
  id: string;

  @Column()
  name: string;

  @Column({ nullable: true })
  region?: string;

  @OneToMany(() => PokemonEntry, (entry) => entry.trainer, { cascade: true })
  roster: PokemonEntry[];
}

@Entity() markiert die Klasse als "das hier wird eine Datenbanktabelle". Jedes @Column() wird eine Spalte. @PrimaryGeneratedColumn('uuid') erzeugt automatisch eine eindeutige ID beim Anlegen (eine UUID statt einer simplen Zahl — verhindert, dass sich jemand von außen einfach IDs "erraten" kann, z. B. id=1, id=2).

@OneToMany beschreibt eine Beziehung: ein Trainer hat viele PokemonEntry-Einträge (sein Team/Roster). Das ist die Objekt-Sicht auf das, was in relationalen Datenbanken über einen Fremdschlüssel gelöst wird.

backend/src/trainers/pokemon-entry.entity.ts
@Entity()
export class PokemonEntry {
  @PrimaryGeneratedColumn('uuid')
  id: string;

  @Column()
  speciesName: string;

  @Column()
  level: number;

  @Column({ default: false })
  isLegendary: boolean;

  @Column({ nullable: true })
  heldItem?: string;

  @ManyToOne(() => Trainer, (trainer) => trainer.roster, { onDelete: 'CASCADE' })
  trainer: Trainer;

  @Column()
  trainerId: string;
}

Die Gegenseite der Beziehung: @ManyToOne — viele PokemonEntry-Zeilen gehören zu einem Trainer. trainerId ist der tatsächliche Fremdschlüssel in der Datenbank; trainer ist die bequeme Objekt-Referenz, die TypeORM automatisch aus diesem Fremdschlüssel auflöst, wenn du danach fragst (siehe relations: ['roster'] in Schritt 10).

Warum onDelete: 'CASCADE'? Wenn ein Trainer gelöscht wird, sollen seine Pokémon-Einträge nicht als "Datenleichen" ohne gültigen Trainer zurückbleiben — die Datenbank löscht sie automatisch mit. Das ist eine Entscheidung, die du in Stage 1 deines Architektur-Vorschlags (siehe EXERCISE.md) bewusst treffen und begründen solltest, nicht einfach dem Default überlassen.

Schritt 7TournamentRule & Violation

backend/src/rules/tournament-rule.entity.ts

Diese Entity beschreibt eine Turnier-Regel: ein optionales Level-Limit, eine optionale Höchstzahl an legendären Pokémon, eine Liste verbotener Items. Beachte: alle Felder außer name/description sind nullable bzw. haben einen Default — eine Regel muss nicht alle Aspekte gleichzeitig prüfen. Das noDuplicateSpecies-Feld existiert schon (Default false), wird aber aktuell von keiner Logik ausgewertet — das ist die Übungsaufgabe aus EXERCISE.md, die du nach diesem Tutorial angehst.

backend/src/violations/violation.entity.ts
export enum ViolationSeverity {
  LOW = 'LOW',
  MEDIUM = 'MEDIUM',
  HIGH = 'HIGH',
}

@Entity()
export class Violation {
  @PrimaryGeneratedColumn('uuid')
  id: string;

  @ManyToOne(() => Trainer, { onDelete: 'CASCADE' })
  trainer: Trainer;

  @Column() trainerId: string;
  @Column() ruleId: string;
  @Column() ruleName: string;

  @Column({ type: 'simple-enum', enum: ViolationSeverity })
  severity: ViolationSeverity;

  @Column() details: string;

  @CreateDateColumn()
  createdAt: Date;
}

Ein enum (Aufzählungstyp) statt eines einfachen string-Felds für severity stellt sicher, dass in der Datenbank niemals ein Tippfehler wie "HIHG" landet — TypeScript lässt zur Kompilierzeit nur die drei definierten Werte zu.

Warum ruleName zusätzlich zu ruleId speichern (Denormalisierung)? Eigentlich "unsauber" im klassischen Datenbank-Sinn (der Name steht ja schon in der TournamentRule-Tabelle). Aber: Regeln könnten sich später ändern oder gelöscht werden — der Audit-Trail (siehe Compliance-Kapitel im Interview-Guide) muss trotzdem zeigen, wie die Regel zum Zeitpunkt des Verstoßes hieß. Das ist ein bewusster Trade-off zwischen Datenbank-Reinheit und Nachvollziehbarkeit — genau die Art Trade-off, die du im Architektur-Vorschlag benennen solltest.

Schritt 8RuleEngineService (reine Logik)

backend/src/rules/rule-engine.service.ts

Jetzt kommt der wichtigste Baustein des ganzen Projekts — und der am meisten missverstandene Teil bei NestJS-Einsteigern: Dieser Service hat keinen einzigen Konstruktor-Parameter, kein @InjectRepository, keine Datenbank-Berührung. 

@Injectable()
export class RuleEngineService {
  checkRoster(roster: PokemonEntry[], rule: TournamentRule): RuleCheckResult[] {
    const results: RuleCheckResult[] = [];

    if (rule.maxLevel != null) {
      for (const p of roster) {
        if (p.level > rule.maxLevel) {
          results.push({ severity: ViolationSeverity.MEDIUM, details: `${p.speciesName} ...` });
        }
      }
    }
    // ... weitere Regeln (maxLegendaries, bannedItems) ...
    return results;
  }
}
Warum absichtlich KEINE Datenbank-Abhängigkeit? Das ist das Prinzip "Trennung von Business-Logik und Infrastruktur" (auch Hexagonal/Clean Architecture genannt, siehe Interview-Guide Kapitel "Architektur & Vorgehen"). Diese Funktion bekommt fertige Daten hineingereicht (ein Array, ein Regel-Objekt) und gibt fertige Ergebnisse zurück — sie weiß nichts davon, ob diese Daten aus SQLite, HANA oder einem Unit-Test-Fake kommen. Der Effekt: Du kannst diese Logik in Millisekunden testen, ohne Datenbank, ohne HTTP-Server, ohne irgendetwas zu mocken außer den reinen Eingabedaten (siehe Schritt 9).
Der typische Anfängerfehler wäre gewesen: Diese Prüf-Logik direkt in den ComplianceService zu schreiben (der die Datenbank kennt). Dann könntest du die Regel-Logik nicht mehr isoliert testen, ohne jedes Mal eine Datenbank-Verbindung aufzubauen — Tests würden langsam und umständlich, und genau solche Tests werden in der Praxis oft übersprungen. Kleine Architektur-Entscheidung, großer Effekt auf Testbarkeit.

Schritt 9Der erste Test (Jest-Grundlagen)

backend/src/rules/rule-engine.service.spec.ts

Warum testen wir RuleEngineService als Allererstes, noch bevor es überhaupt einen HTTP-Endpunkt gibt, der ihn nutzt? Weil er die reinste, am leichtesten isolierbare Logik im ganzen Projekt ist — der ideale Startpunkt, um Testen zu lernen.

Grundvokabular von Jest

FunktionBedeutung
describe('Name', () => {...})Gruppiert zusammengehörige Tests, rein organisatorisch
it('sollte X tun', () => {...}) (oder test(...))Ein einzelner Testfall
expect(wert).toBe(erwartet)Eine "Behauptung" (Assertion) — schlägt der Test fehl, wenn falsch

Das Arrange-Act-Assert-Muster

it('meldet einen Verstoss, wenn ein Pokemon das Level-Limit ueberschreitet', () => {
  // ARRANGE: Testdaten vorbereiten
  const roster = [pokemon({ level: 60, speciesName: 'Charizard' })];

  // ACT: die zu testende Funktion aufrufen
  const result = service.checkRoster(roster, rule({ maxLevel: 50 }));

  // ASSERT: prüfen, ob das Ergebnis stimmt
  expect(result).toHaveLength(1);
  expect(result[0].details).toContain('Charizard');
});

Jeder gute Test folgt dieser Dreiteilung: erst die Ausgangslage herstellen, dann genau EINE Sache tun, dann prüfen. Die kleinen Hilfsfunktionen pokemon(...) und rule(...) oben in der Datei bauen Test-Objekte mit sinnvollen Defaults, damit jeder einzelne Test nur die Felder angeben muss, die für diesen konkreten Fall wichtig sind — das hält Tests lesbar.

Warum it.skip(...) bei einem der Tests? Das ist die Übungsaufgabe: Ein Test kann existieren, aber absichtlich übersprungen werden, bis die zugehörige Funktionalität implementiert ist. Das ist ein leichter Einstieg in testgetriebene Entwicklung (TDD): Erst den Test schreiben (der beschreibt, was passieren soll), dann die Implementierung nachziehen, bis er grün wird. Genau das machst du in EXERCISE.md Stage 4b.

Schritt 10Repository, Service, Controller

Jetzt bauen wir eine typische "CRUD-Schicht" (Create/Read/Update/Delete) — am Beispiel Trainers. Drei Dateien, drei klar getrennte Aufgaben. Das ist ein Muster, das sich für rules und violations praktisch identisch wiederholt.

backend/src/trainers/trainers.service.ts
@Injectable()
export class TrainersService {
  constructor(@InjectRepository(Trainer) private readonly repo: Repository<Trainer>) {}

  findAll(): Promise<Trainer[]> {
    return this.repo.find({ relations: ['roster'] });
  }

  async findOne(id: string): Promise<Trainer> {
    const trainer = await this.repo.findOne({ where: { id }, relations: ['roster'] });
    if (!trainer) throw new NotFoundException(`Trainer ${id} nicht gefunden`);
    return trainer;
  }
}

@InjectRepository(Trainer) ist die konkrete NestJS/TypeORM-Umsetzung des DI-Prinzips aus Schritt 1: "Gib mir das Repository, das für die Trainer-Entity zuständig ist." Die Option relations: ['roster'] sagt TypeORM: "Lade beim Abfragen auch gleich die verknüpften PokemonEntry-Zeilen mit" — sonst bekämst du nur den Trainer ohne sein Team (Stichwort N+1-Problem, siehe Interview-Guide Kapitel "TypeORM").

Warum wirft findOne selbst eine NotFoundException, statt einfach null zurückzugeben? Damit sich jeder Aufrufer (Controller, andere Services) nicht wiederholt um den "nicht gefunden"-Fall kümmern muss. NestJS fängt diese Exception automatisch ab und wandelt sie in eine passende HTTP-404-Antwort um — Fehlerbehandlung an einer einzigen Stelle statt überall verstreut.
backend/src/trainers/trainers.controller.ts
@Controller('trainers')
export class TrainersController {
  constructor(private readonly service: TrainersService) {}

  @Get()
  findAll() { return this.service.findAll(); }

  @Get(':id')
  findOne(@Param('id') id: string) { return this.service.findOne(id); }
}

Der Controller ist bewusst "dünn" — er enthält keine Geschäftslogik, sondern übersetzt nur zwischen HTTP (URLs, Methoden, Statuscodes) und dem Service. @Controller('trainers') plus @Get() ergibt die Route GET /trainers; @Get(':id') ergibt GET /trainers/:id, wobei @Param('id') den URL-Platzhalter als Funktionsparameter einspeist.

Warum Controller und Service überhaupt trennen? Der Controller kennt HTTP-Details (Routen, Statuscodes), der Service kennt Geschäftslogik/Datenzugriff — Single Responsibility Principle. Der praktische Nutzen: Du könntest dieselbe TrainersService-Logik später auch von einem Pub/Sub-Consumer statt einem HTTP-Controller aus aufrufen, ohne sie zu duplizieren.

Schritt 11Ein Modul komplett verkabeln

backend/src/trainers/trainers.module.ts
@Module({
  imports: [TypeOrmModule.forFeature([Trainer, PokemonEntry])],
  controllers: [TrainersController],
  providers: [TrainersService],
  exports: [TrainersService],
})
export class TrainersModule {}

Das ist oft die verwirrendste Stelle für NestJS-Einsteiger — hier die Bedeutung jedes Feldes einzeln:

FeldBedeutung
importsWas dieses Modul von außen braucht. TypeOrmModule.forFeature([...]) registriert genau die Entities, für die dieses Modul Repositories per @InjectRepository anfragen darf
controllersWelche HTTP-Routen dieses Modul nach außen anbietet
providersWelche injizierbaren Klassen (Services) innerhalb dieses Moduls existieren
exportsWelche dieser Provider auch andere Module nutzen dürfen, wenn sie dieses Modul importieren
Warum exports: [TrainersService]? Schau voraus zu Schritt 12: Der ComplianceService braucht Zugriff auf Trainer-Daten. Ohne den Export wäre TrainersService ein rein internes Detail von TrainersModule, das kein anderes Modul sehen könnte — bewusste Kapselung, wie private in objektorientierten Sprachen, nur auf Modul-Ebene.

rules.module.ts und violations.module.ts folgen exakt demselben Muster — schau sie dir kurz an, du wirst die Struktur sofort wiedererkennen. Der einzige Unterschied bei rules.module.ts: es registriert zusätzlich RuleEngineService als Provider (den reinen Logik-Baustein aus Schritt 8) und exportiert ihn ebenfalls, weil ComplianceService ihn gleich braucht.

Schritt 12ComplianceService & Transaktionen

backend/src/compliance/compliance.service.ts

Jetzt kommt das Herzstück: der Service, der alles bisher Gebaute zusammenführt. Er lädt einen Trainer und eine Regel, lässt RuleEngineService (Schritt 8) die reine Prüfung durchführen, speichert das Ergebnis — und das alles transaktional. 

const savedViolations = await this.dataSource.transaction(async (manager) => {
  const violations = findings.map((finding) =>
    manager.create(Violation, { trainerId: trainer.id, ruleId: rule.id, ...finding }),
  );
  return violations.length ? manager.save(Violation, violations) : [];
});

Was ist eine Transaktion und warum brauchen wir sie hier?

Eine Transaktion garantiert: entweder werden alle Änderungen darin gespeichert, oder keine — nie ein halb fertiger Zustand. Stell dir vor, ein Team hat 3 Regelverstöße gleichzeitig. Ohne Transaktion könnte theoretisch Violation 1 gespeichert werden, dann würde die Anwendung abstürzen (Stromausfall, Netzwerkfehler, Bug), und Violation 2+3 fehlen — dein Compliance-System würde einen unvollständigen, irreführenden Zustand zeigen. Bei einem Compliance-Feature ist das nicht nur ein technischer Fehler, sondern ein Vertrauensproblem: Die Daten müssen konsistent sein, damit ein Audit ihnen glauben kann.

Warum wird das Publizieren des Events (Schritt 13) NICHT Teil derselben Transaktion? Schau dir den Code genau an: this.publisher.publish(...) steht außerhalb des transaction(...)-Blocks. Das ist Absicht: Eine Datenbank-Transaktion kann man zurückrollen, einen bereits an ein Pub/Sub-System gesendeten Event-Aufruf nicht. Würden wir das Publizieren in die Transaktion packen und die Transaktion würde später fehlschlagen, hätten wir ein Event über etwas verschickt, das gar nicht passiert ist. Deshalb: erst sicher speichern, dann informieren.

Schritt 13Ports & Adapters (Pub/Sub-Simulation)

backend/src/events/publisher.port.ts
export interface PublisherPort {
  publish(topic: string, payload: Record<string, unknown>): Promise<void>;
}
export const PUBLISHER_PORT = Symbol('PUBLISHER_PORT');

Das Problem

Die Ausschreibung nennt GCP Pub/Sub als echten Event-Transport. Aber: Für dieses Lernprojekt willst du weder ein GCP-Konto einrichten noch beim Testen echte Netzwerk-Aufrufe machen. Trotzdem willst du das Muster — "wenn etwas Wichtiges passiert, informiere andere Systeme, ohne sie zu kennen" — schon jetzt richtig anlegen.

Die Lösung: ein Interface (Port) plus austauschbare Implementierung (Adapter)

PublisherPort beschreibt nur was möglich sein muss ("etwas auf einem Topic publizieren"), nicht wie. ComplianceService kennt nur dieses Interface (siehe @Inject(PUBLISHER_PORT) im Konstruktor), nicht die konkrete Implementierung.

backend/src/events/in-memory-publisher.adapter.ts
@Injectable()
export class InMemoryPublisherAdapter implements PublisherPort {
  async publish(topic: string, payload: Record<string, unknown>): Promise<void> {
    this.logger.log(`Event publiziert auf "${topic}": ${JSON.stringify(payload)}`);
    this.recent.unshift({ topic, payload, publishedAt: new Date() });
  }
}

Lokal "publiziert" dieser Adapter nur in eine Liste im Arbeitsspeicher (abrufbar über GET /events/recent). In der echten Plattform gäbe es eine zweite Klasse, GcpPubSubPublisherAdapter, die intern den @google-cloud/pubsub-Client nutzt — mit identischer publish()-Signatur. ComplianceService müsste dafür keine einzige Zeile ändern.

backend/src/events/events.module.ts
providers: [
  InMemoryPublisherAdapter,
  { provide: PUBLISHER_PORT, useExisting: InMemoryPublisherAdapter },
],
Warum ein Symbol als Token (PUBLISHER_PORT) statt einfach die Klasse zu injizieren? TypeScript-Interfaces existieren nur zur Kompilierzeit — zur Laufzeit "verschwinden" sie komplett (siehe auch Interview-Guide Kapitel "TypeScript"). Der DI-Container von NestJS braucht aber zur Laufzeit einen konkreten Schlüssel, um nachzuschlagen, was er liefern soll. Ein Symbol ist ein garantiert eindeutiger, laufzeitfähiger Ersatz für "das Interface PublisherPort". Das useExisting sagt: "wenn nach PUBLISHER_PORT gefragt wird, liefere die bereits existierende InMemoryPublisherAdapter-Instanz."

OnModuleInit ist ein Lifecycle-Hook: NestJS ruft onModuleInit() automatisch auf, sobald alle Abhängigkeiten des Moduls aufgebaut sind, aber bevor die App tatsächlich Requests annimmt. Perfekt für einmalige Initialisierungsarbeit wie Testdaten.

backend/src/compliance/compliance.service.spec.ts

jest.fn() erzeugt eine "Attrappe" einer Funktion: Sie tut standardmäßig nichts, aber Jest merkt sich jeden Aufruf. TypeORM selbst betreffen. Ein Test sollte immer nur EINE Sache prüfen.

Führe npm run test im backend/-Ordner aus und beobachte, wie beide Test-Dateien (rule-engine.service.spec.ts und compliance.service.spec.ts) zusammen laufen — zusammen bilden sie die "Unit-Test-Ebene" deiner künftigen Testpyramide (siehe Schritt 24).

Schritt 17Warum Angular & Standalone Components

Das Backend liefert jetzt Daten über HTTP. Zeit für die Oberfläche. Kurzer Blick auf die grundsätzliche Frage: Warum überhaupt ein Framework wie Angular, statt HTML mit ein bisschen JavaScript zu schreiben?

Sobald eine Oberfläche mehr als ein paar statische Elemente hat — Zustand (welcher Trainer ist ausgewählt?), Reaktion auf Nutzereingaben, Kommunikation mit einem Backend — wird "von Hand" schnell unübersichtlich. Angular gibt dir eine Struktur (Komponenten, Services, Dependency Injection — ja, dasselbe DI-Prinzip wie im Backend, siehe Schritt 1!) und kümmert sich automatisch darum, das DOM (die tatsächlich angezeigte Seite) synchron zu deinem Datenzustand zu halten.

frontend/src/app/app.component.ts
@Component({
  selector: 'app-root',
  standalone: true,
  imports: [RouterOutlet, RouterLink, RouterLinkActive],
  template: `...`,
})
export class AppComponent {}

standalone: true ist der moderne Angular-Ansatz (seit Angular 14, mittlerweile Standard): Eine Komponente importiert direkt, was sie braucht (imports: [...]), statt über ein zentrales NgModule registriert zu werden. Weniger Boilerplate, klarere Abhängigkeiten pro Komponente — du siehst direkt am Komponenten-Code, was sie braucht, statt in einer separaten Modul-Datei suchen zu müssen.

Schritt 19Models & ApiService

frontend/src/app/core/models.ts

Diese Datei dupliziert bewusst die Form der Backend-Entities als TypeScript-interfaces (kein @Column, keine Decorators — reine Typinformation, es gibt hier keine Datenbank). In größeren Projekten würde man diese Typen oft automatisch aus einer OpenAPI-Spezifikation des Backends generieren, damit Frontend und Backend nie auseinanderlaufen — hier von Hand geschrieben, um das Prinzip klar zu halten.

frontend/src/app/core/api.service.ts
@Injectable({ providedIn: 'root' })
export class ApiService {
  private http = inject(HttpClient);

  getTrainers(): Observable<Trainer[]> {
    return this.http.get<Trainer[]>(`${BASE_URL}/trainers`);
  }

  checkRoster(trainerId: string, ruleId: string): Observable<ComplianceCheckResult> {
    return this.http.post<ComplianceCheckResult>(`${BASE_URL}/compliance/check`, { trainerId, ruleId });
  }
}

inject(HttpClient) ist eine neuere Alternative zu Konstruktor-Injection (funktioniert nur an bestimmten Stellen wie Feldinitialisierern, ist aber bei Standalone-Komponenten/Services sehr verbreitet) — dasselbe DI-Prinzip, nur andere Syntax.

Was ist ein Observable?

HttpClient-Methoden geben kein Promise zurück, sondern ein Observable (aus der Bibliothek RxJS). Der Unterschied: Ein Promise löst sich genau einmal auf. Ein Observable kann mehrfach Werte liefern (z. B. bei WebSockets) und liefert nichts, bis jemand .subscribe(...) aufruft — "faul" statt sofort ausgeführt. Für einen einfachen HTTP-Request wie hier verhält es sich im Alltag sehr ähnlich zu einem Promise; du wirst .subscribe(...) gleich in Schritt 21 in Aktion sehen.

Warum ein zentraler ApiService statt HttpClient direkt in jeder Komponente zu nutzen? Dieselbe Begründung wie Controller/Service im Backend (Schritt 10): Wenn sich die Backend-URL oder das Antwortformat ändert, gibt es genau eine Stelle zum Anpassen. Und Komponenten bleiben einfacher testbar, weil man in Tests nur ApiService faken muss, nicht das komplette HTTP-System.

Schritt 20Signals verstehen

Bevor wir die erste richtige UI-Komponente bauen: Angular Signals sind das neue Reaktivitätsmodell (seit Angular 16/17) und werden in beiden Komponenten dieses Projekts genutzt.

Das Problem, das Signals lösen

Wenn sich Daten ändern (z. B. die Liste der Trainer wurde vom Backend geladen), muss die angezeigte Seite automatisch mit-aktualisiert werden — ohne dass du manuell "DOM neu zeichnen" aufrufst. Früher löste Angular das über Zone.js (ein Mechanismus, der praktisch jede asynchrone Operation im Browser abfängt und danach die gesamte Komponente neu prüft). Signals lösen das feingranularer. 

trainers = signal<Trainer[]>([]);   // ein reaktiver Wert, Startwert: leeres Array

// Lesen: wie ein Funktionsaufruf
console.log(this.trainers());

// Schreiben: komplett ersetzen
this.trainers.set(neueListe);

// Schreiben: basierend auf altem Wert
this.trainers.update(alte => [...alte, neuerTrainer]);
Warum signal() statt einfach eines normalen Klassenfelds (trainers: Trainer[] = [])? Ein normales Feld ändert sich, aber Angular "merkt" das nicht automatisch — bei der klassischen Zone.js-Strategie wird trotzdem die ganze Komponente neu geprüft (unnötige Arbeit), bei OnPush-Komponenten würde eine reine Feldänderung sogar komplett unbemerkt bleiben. Ein Signal hingegen "weiß", wo genau im Template es benutzt wird, und triggert gezielt nur die nötige Aktualisierung. Für dieses kleine Projekt macht der Performance-Unterschied kaum etwas aus — aber du lernst hier direkt die moderne, zukunftssichere Angular-Schreibweise statt eines auslaufenden Musters.

Schritt 21RosterCheckComponent im Detail

frontend/src/app/compliance/roster-check.component.ts

Diese Komponente ist der zentrale User-Flow der ganzen App. Gehen wir sie in der Reihenfolge durch, in der sie tatsächlich abläuft.

1. Zustand definieren

trainers = signal<Trainer[]>([]);
rules = signal<TournamentRule[]>([]);
result = signal<ComplianceCheckResult | null>(null);
loading = signal(false);
selectedTrainerId = '';
selectedRuleId = '';

Vier Signals für Daten, die sich über Zeit ändern und im Template angezeigt werden, plus zwei einfache Felder für die aktuelle Dropdown-Auswahl (die über [(ngModel)] automatisch synchron gehalten werden, dafür braucht es hier kein Signal — FormsModule übernimmt das).

2. Beim Erstellen der Komponente: Daten laden

constructor() {
  this.api.getTrainers().subscribe((t) => this.trainers.set(t));
  this.api.getRules().subscribe((r) => this.rules.set(r));
}

Hier siehst du .subscribe(...) aus Schritt 19 in Aktion: "Wenn die Antwort vom Backend ankommt, aktualisiere das Signal." Zwei unabhängige Requests laufen parallel (keiner wartet auf den anderen).

3. Nutzeraktion: Prüfen-Button

check() {
  this.loading.set(true);
  this.api.checkRoster(this.selectedTrainerId, this.selectedRuleId).subscribe({
    next: (res) => { this.result.set(res); this.loading.set(false); },
    error: () => this.loading.set(false),
  });
}

loading wird bewusst vor dem Request auf true gesetzt und in beiden Fällen (Erfolg und Fehler) wieder zurückgesetzt — sonst würde bei einem Netzwerkfehler der Button für immer im "Prüfe…"-Zustand hängen bleiben.

4. Das Template reagiert automatisch

<button (click)="check()" [disabled]="!selectedTrainerId || !selectedRuleId || loading()">
  {{ loading() ? 'Prüfe…' : 'Prüfen' }}
</button>

@if (result(); as res) {
  @if (res.isCompliant) {
    <p>✅ Regelkonform</p>
  } @else {
    <ul>
      @for (v of res.violations; track v.id) {
        <li>[{{ v.severity }}] {{ v.details }}</li>
      }
    </ul>
  }
}

@if/@for sind die neue Control-Flow-Syntax (seit Angular 17, ersetzt die älteren *ngIf/*ngFor-Direktiven). @if (result(); as res) liest das Signal einmal aus und merkt sich den Wert unter res für den ganzen Block — sonst müsste man result() mehrfach aufrufen. track v.id bei @for sagt Angular, wie es einzelne Listeneinträge wiedererkennt, um beim Neu-Rendern nur geänderte DOM-Elemente anzufassen statt alles neu zu bauen.

Der komplette Kreislauf dieser Komponente: Konstruktor lädt Daten → Nutzer wählt Trainer + Regel per Dropdown → Klick auf "Prüfen" → ApiService schickt POST /compliance/check → Backend durchläuft ComplianceController → ComplianceService → RuleEngineService (Schritte 10-12) → Antwort kommt zurück → result-Signal wird gesetzt → Template rendert automatisch neu. Das ist der komplette Weg einer einzigen Nutzeraktion durch alle Schichten dieses Tutorials.

Schritt 22ViolationListComponent & Pipes

frontend/src/app/compliance/violation-list.component.ts

Strukturell fast identisch zu Schritt 21 (Daten im Konstruktor laden, in ein Signal schreiben, im Template mit @for ausgeben) — der einzige neue Baustein hier:

Schritt 24Warum Jest UND Cypress?

Schritt 25Der Cypress-Test im Detail

frontend/cypress/e2e/roster-compliance.cy.ts
beforeEach(() => {
  cy.intercept('GET', '**/trainers', { fixture: 'trainers.json' }).as('getTrainers');
  cy.intercept('GET', '**/rules', { fixture: 'rules.json' }).as('getRules');
  cy.visit('/check');
  cy.wait(['@getTrainers', '@getRules']);
});

Warum wird hier das echte Backend NICHT gebraucht?

cy.intercept(...) fängt den Netzwerk-Request ab, bevor er den Browser verlässt, und beantwortet ihn stattdessen mit einer Fixture — vorbereiteten JSON-Testdaten aus cypress/fixtures/trainers.json. Das macht den Test schnell, zuverlässig (kein zufälliges Fehlschlagen wegen eines langsamen Backends) und unabhängig davon, ob gerade ein Backend läuft. Der Test prüft ausschließlich: "verhält sich das Frontend richtig, gegeben diese Antwort?" — nicht, ob das Backend selbst korrekt ist (das prüfen die Jest-Tests aus Schritt 16). 

it('zeigt Verstöße an, wenn das Team nicht regelkonform ist', () => {
  cy.intercept('POST', '**/compliance/check', { fixture: 'violation-result.json' }).as('checkRoster');

  cy.get('select').eq(0).select('Trainer Bo');
  cy.get('select').eq(1).select('Great League Cap');
  cy.contains('button', 'Prüfen').click();

  cy.wait('@checkRoster');
  cy.contains('Verstoß/Verstöße gefunden').should('be.visible');
});

cy.get(...) sucht Elemente wie ein echter Nutzer (über sichtbaren Text/Selektoren), .select(...)/.click() simulieren echte Interaktion, cy.wait('@checkRoster') wartet gezielt, bis der zuvor definierte Intercept tatsächlich ausgelöst wurde — kein zufälliges sleep(1000) nötig, Cypress wartet automatisch (Retry-Ability), bis Bedingungen erfüllt sind.

Schritt 26Warum CI/CD überhaupt?

Bisher hast du alles lokal auf deinem Rechner laufen lassen. Das Problem in einem echten Team: "Auf meinem Rechner hat's funktioniert" ist kein verlässlicher Qualitätsnachweis — unterschiedliche Node-Versionen, vergessene lokale Änderungen, oder schlicht ein übersehener fehlgeschlagener Test können durchrutschen.

CI (Continuous Integration) heißt: Bei jeder Änderung laufen Build und Tests automatisch, auf einer neutralen, sauberen Maschine — nicht auf deinem Rechner. CD (Continuous Delivery/Deployment) baut darauf auf: Wenn alles grün ist, kann automatisch (oder nach manueller Freigabe) ausgeliefert werden. Genau das bildet dieses Projekt zweimal ab — einmal mit GitHub Actions, einmal mit Jenkins, weil beide in deiner Stellenausschreibung genannt sind.

Schritt 27ci.yml Zeile für Zeile

.github/workflows/ci.yml
on:
  pull_request: { branches: [main] }
  push: { branches: [main] }

Der Workflow läuft bei jedem Pull Request gegen main und bei jedem Push auf main selbst.

jobs:
  backend:
    steps:
      - run: npm install
      - run: npm run test -- --coverage
      - run: npm run build

Ein Job ist eine Gruppe von Schritten, die auf einer frischen virtuellen Maschine läuft. backend und frontend sind zwei unabhängige Jobs — sie laufen standardmäßig parallel, nicht nacheinander, weil sie einander nicht brauchen. Das spart Zeit. 

e2e:
  needs: [backend, frontend]

needs erzwingt eine Reihenfolge: Der e2e-Job (Cypress) wartet, bis backend UND frontend erfolgreich durchgelaufen sind. Das ist absichtlich so gestaffelt: Es wäre Zeitverschwendung, die langsamen End-to-End-Tests zu starten, wenn schon die schnellen Unit-Tests fehlschlagen. 

deploy:
  needs: [e2e]
  if: github.ref == 'refs/heads/main'
  environment: production
Das Approval-Gate: environment: production kombiniert mit "Required Reviewers" in den GitHub-Repo-Einstellungen sorgt dafür, dass dieser Job pausiert und auf eine manuelle Bestätigung wartet, bevor er läuft — das ist die technische Umsetzung von "achieve approval" / "release after confirmation" aus deiner Stellenausschreibung, nicht nur ein Textbaustein, sondern ein echter Kontrollpunkt in der Pipeline.

Der komplette Kreislauf

Zum Schluss der ganze Weg einer einzigen Nutzeraktion, einmal von vorne bis hinten durch jede Schicht, die du in diesem Tutorial gebaut hast:

  1. Nutzer klickt "Prüfen" im Browser → RosterCheckComponent.check() (Schritt 21)
  2. ApiService schickt POST /compliance/check per HttpClient (Schritt 19)
  3. ComplianceController nimmt den Request an, ValidationPipe prüft das DTO (Schritt 3, 10)
  4. ComplianceService lädt Trainer + Regel über die jeweiligen Repositories (Schritt 12)
  5. RuleEngineService prüft das Roster gegen die Regel — reine Logik, keine DB (Schritt 8)
  6. Gefundene Verstöße werden transaktional als Violation-Zeilen gespeichert (Schritt 12)
  7. Bei Verstößen: PublisherPort "publiziert" ein Event (Schritt 13)
  8. Antwort geht als JSON zurück zum Frontend
  9. result-Signal wird gesetzt, Template rendert automatisch neu (Schritt 20-21)

Und zwei Sicherheitsnetze, die bei jeder Code-Änderung an diesem Kreislauf automatisch mitlaufen: die Jest-Tests (Schritt 9, 16) prüfen die Logik-Bausteine isoliert, der Cypress-Test (Schritt 25) prüft den kompletten Ablauf aus Nutzersicht, und die CI-Pipeline (Schritt 27-28) sorgt dafür, dass das bei jeder Änderung automatisch passiert, bevor irgendetwas Produktion erreicht.
